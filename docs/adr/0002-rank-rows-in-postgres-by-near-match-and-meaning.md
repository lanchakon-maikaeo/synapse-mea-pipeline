# จัดอันดับแถวใน Postgres ด้วยการค้นแบบใกล้เคียงร่วมกับการค้นเชิงความหมาย แทนการให้ LLM จัดอันดับ

ผู้ใช้ตอบ grill รอบแรก Q6, รอบสอง Q1, รอบสาม Q1–Q3 และรอบสี่ Q1 (ใช้ Cloudflare Workers AI แผนฟรี) วันที่ 22 พฤศจิกายน 2569 เดิม `query_database` ค้นแถวด้วยข้อความที่ต้องตรงทุกตัวอักษร แล้วส่งแถวที่ได้ให้ Typhoon จัดอันดับ แต่ชื่อพัสดุ 6,193 จาก 7,596 รายการ (82%) เป็นภาษาอังกฤษแบบย่อ ผู้ใช้ที่พิมพ์ "ล่อฟ้า" จึงควรเจอ "SURGE ARRESTER" ต่อไปนี้ฐานข้อมูลจะจัดอันดับแถวเอง โดยรวมอันดับจากการค้นแบบใกล้เคียง (pg_trgm) กับการค้นเชิงความหมาย (embedding จาก BGE-M3 บน Cloudflare Workers AI ใช้โควตาฟรี และเก็บใน pgvector) จึงไม่ต้องส่งแถวให้ LLM และลดการเรียก Typhoon ได้หนึ่งครั้งต่อการค้น

- คำค้นที่ส่งไปทำ embedding ต้องผ่านการปิดข้อมูลก่อนส่ง AI ตาม ADR 0001 ส่วนชื่อพัสดุเป็นข้อมูลงาน จึงส่งไปทำ embedding ได้
- ถ้ายังไม่มีคีย์ embedding, โควตาฟรีของวันนั้นหมด หรือมีการหยุดใช้ AI ของงานค้นเชิงความหมาย ระบบใช้การค้นแบบใกล้เคียงอย่างเดียว
- **ขอบเขต (รอบสาม Q2):** ทุกบทบาทค้นได้ ฐานข้อมูลกรองผลค้นตามขอบเขตของบทบาทก่อนส่งออกจาก server ไม่ปล่อยให้ AI เลือกเอง บทบาทที่ไม่ใช่เจ้าหน้าที่เขตยังไม่ผูกกับเขต
- **รายการใกล้เคียง (รอบสาม Q3):** ช่องค้นพัสดุในหน้าคำแนะนำ (Intelligence), หน้า FIFO และหน้ายอดใช้จริงของเขต ยังกรองแบบตรงตัวเหมือนเดิม ถ้าไม่เจอจะแสดงพัสดุที่ความหมายเดียวกันไม่เกินห้ารายการ แม้ตัวอักษรไม่ตรง
- การเลือกแหล่งข้อมูลยังให้ LLM จัดอันดับ โดยส่งชื่อ คำอธิบาย และคอลัมน์หลักของตาราง ไม่ส่งแถว (ดูหัวข้อ "เลือกแหล่งข้อมูลจากคอลัมน์และชื่อในทะเบียน")
- คลังเอกสารจะค้นด้วยวิธีเดียวกันเมื่อมีเอกสารจริง

## ตัดคำไทยด้วย OpenThai2.0-LATTE-WordSeg-Lite (เพิ่ม 24 พฤศจิกายน 2569)

ผู้ใช้ขอให้ใช้ตัวตัดคำ [OpenThai2.0-LATTE-WordSeg-Lite](https://huggingface.co/iapp/OpenThai2.0-LATTE-WordSeg-Lite) ของ iApp กับคำค้นภาษาไทย ตัวนี้ไม่ต้องตั้ง server Python แบบที่ทำให้ไม่เลือก PyThaiNLP เพราะแปลง runtime 428 บรรทัดเป็น JavaScript แล้วรันไฟล์ ONNX ขนาด 3 MB ด้วย onnxruntime-web ใน function ของแชตได้เลย เมื่อเทียบกับ runtime Python บนข้อความไทย 3,012 บรรทัดจาก repo นี้ ได้คำตรงกันทุกบรรทัด

- คำค้น (`search`) ถูกตัดเป็นคำก่อนส่งฐานข้อมูล ฐานข้อมูลถือว่าเจอเมื่อแถวมีครบทุกคำ ไม่ต้องเรียงลำดับ เช่น "250kVA หม้อแปลงไฟฟ้า" เจอ "หม้อแปลงไฟฟ้า 3 เฟส 22kV 250kVA"
- ตัวกรอง `contains` ยังต้องตรงตัวเหมือนเดิม เพราะใช้คำนวณยอดรวม ถ้าขยายให้กว้างขึ้น ยอดรวมจะเปลี่ยน
- ถ้าโหลดหรือรันโมเดลไม่ได้ ระบบกลับไปใช้ ICU แชตจึงไม่ล้มเพราะตัดคำไม่ได้
- การคัดแหล่งข้อมูลก่อนให้ LLM จัดอันดับยังใช้ ICU (แก้ 25 พฤศจิกายน 2569) หลังขึ้น production LATTE ตัด "เต้ารับ" เป็น "เต้า | รับ" คำว่า "รับ" ไปตรงคำอธิบายตารางรับเข้า ทำให้เหลือ 30 ตารางที่ไม่มี `core.materials` คำถามชื่อวัสดุจึงไปค้นตารางคลังแทน ส่วนคำค้นแถวไม่มีปัญหานี้ เพราะฐานข้อมูลหาคำใน "ชื่อวัสดุ" ซึ่ง "เต้า" กับ "รับ" อยู่ติดกันอยู่แล้ว
- การคัดแหล่งข้อมูลนับคำจากข้อความของผู้ใช้ด้วย ไม่ใช่เฉพาะคำค้นที่ LLM เขียน เพราะ LLM มักตัดคำบอกใบ้อย่าง "วัสดุ" ทิ้งเหลือแค่ชื่อวัสดุ
- ถ้ามีไม่ถึง 30 ตารางที่ตรงคำใดคำหนึ่ง LLM จะเห็นทุกตาราง โดยตารางที่ตรงคำอยู่ก่อน ไม่ใช่ตัดส่วนที่เหลือตามลำดับตัวอักษร เดิมคำทั่วไปอย่าง "รหัส" ตรงแค่ 5 ตารางเขต แล้วอีก 25 ช่องถูกเติมตามตัวอักษรจนตัด `core.materials` ทิ้ง แคตตาล็อกทั้งหมด 122 ตารางยาวราว 14,000 ตัวอักษร ยังต่ำกว่าเพดาน 40,000 ของการจัดอันดับ
- LLM ที่จัดอันดับแหล่งข้อมูลเห็นทั้งคำค้นที่ LLM เขียนและคำถามของผู้ใช้ เพราะคำค้นอย่าง "มิเตอร์ไฟฟ้า 1 เฟส" ไม่บอกว่าคำถามต้องหารหัสเขตบางกะปิด้วย ถ้าไม่เห็นคำถาม LLM จะไม่เลือก `core.districts` แล้วไปเดารหัสเขตเอง
- การปิดข้อมูล (ADR 0001) ยังใช้ ICU ตัดสินว่าชื่อต้นยืนเดี่ยวหรือไม่ เพราะการปิดข้อมูลทำงานแบบ synchronous ส่วน onnxruntime ทำงานแบบ asynchronous เท่านั้น
- LATTE ยังตัด "ล่อฟ้า" เป็น "ล่อ | ฟ้า" เหมือน ICU การจับ "ล่อฟ้า" กับ "SURGE ARRESTER" จึงยังต้องรอการค้นเชิงความหมาย
- โมเดลและพจนานุกรมใช้สัญญาอนุญาต CC BY-SA 4.0 ไฟล์ทั้งหมดอยู่ใน `dashboard/app/api/chat/thai-words/` พร้อม NOTICE และที่มา
- function ของแชตใหญ่ขึ้นราว 19 MB (wasm 14.8 MB, โมเดล 3 MB, พจนานุกรม 0.8 MB) และครั้งแรกที่ instance ตัดคำต้องโหลดโมเดลราว 0.3 วินาที

## เลือกแหล่งข้อมูลจากคอลัมน์และชื่อในทะเบียน (เพิ่ม 26 พฤศจิกายน 2569)

ผู้ใช้ขอให้แก้คำถาม "เต้ารับคู่มีขั้วสายดิน มีรหัสอะไร" ที่ตอบผิดบน production และปรับ pipeline ตามงานวิจัยที่รวบรวมไว้ใน `docs/RESEARCH_CHAT_PIPELINE.md` คำอธิบายแหล่งข้อมูลสร้างจากชุดคำหนึ่งชุดต่อหมวด 9 แหล่งในหมวดวัสดุจึงมีคำอธิบายเหมือนกัน `core.materials` ต่างจาก `core.material_packaging` แค่ชื่อตาราง LLM จึงเลือก `core.material_packaging` ซึ่งไม่มีชื่อวัสดุ

- LLM ที่จัดอันดับเห็นคอลัมน์หลักของแต่ละแหล่ง ระบบตัดคอลัมน์ audit และ lineage ออก เรียงคอลัมน์ชื่อและรหัสไว้ก่อน และส่งไม่เกิน 16 คอลัมน์ แคตตาล็อก 122 ตารางพร้อมคอลัมน์ยาวราว 33,000 ตัวอักษร ถ้าเกิน 40,000 ตัวอักษร ระบบส่งแค่ชื่อกับคำอธิบาย
- คอลัมน์อย่างเดียวยังไม่พอ ใน 122 ตาราง คำว่า "รหัส" ตรงกับชุดคำของหมวดเขต ตารางเขต 5 ตารางจึงขึ้นหน้าสุด และ Typhoon เลือกตามลำดับที่เห็น เคสนี้จึงพลาดทั้ง 2 รอบ
- ก่อนจัดอันดับ ระบบค้นคำค้นในทะเบียน ทะเบียนคือแหล่งที่มีคอลัมน์ชื่อตั้งตามชื่อแหล่ง เช่น `core.materials` มี `material_name` ระบบใช้ `contains` ทีละคำกับคอลัมน์ชื่อแล้วนับจำนวนแถว ผ่าน RPC และสิทธิ์ชุดเดียวกับ query ของ LLM ถ้าคอลัมน์ชื่อมีครบทุกคำ ทะเบียนนั้นขึ้นหน้าสุดพร้อม `search_found_in` และจะอยู่ในผลค้นแหล่งข้อมูลเสมอแม้ LLM ไม่เลือก ถ้าค้นไม่สำเร็จ ระบบถือว่าไม่เจอ (value linking แบบเดียวกับ CHESS และ CHASE-SQL)
- ใช้ `contains` กับคอลัมน์ชื่อแทน `search` ทั้งแถว เพราะ `search` หาคำในทุกคอลัมน์ "เขต 5507" จึงไปตรงคลังที่มี `district_id` เป็น 5507
- production มีทะเบียน 6 แหล่ง การค้นแหล่งข้อมูลหนึ่งครั้งจึงถามฐานข้อมูลเพิ่มไม่เกิน 6 ครั้ง ทั้งหมดถามพร้อมกันและนับแถวอย่างเดียวโดยไม่ส่งแถวกลับมา และไม่เรียก LLM เพิ่ม
- `source-ranking-v1` (15 เคส ใช้แคตตาล็อก production 122 ตาราง และแถวทะเบียนวัสดุกับเขต, lock `2f0dc571d639`): main ได้ 93.3% ทั้ง 2 รอบ เพราะเคสเต้ารับพลาดทั้ง 2 รอบ (เลือก `core.material_packaging`) ส่วนที่แก้แล้วได้ 100% ทั้ง 2 รอบ โดย `core.materials` อยู่อันดับ 1
- `chat-heldout-v1` (23 เคส, lock ไม่เปลี่ยน): main ได้ 87.0% ส่วน `8106e41` (เห็นคอลัมน์) ได้ 91.3% ทั้ง 2 รอบ `5ddd723` (ค้นชื่อในทะเบียน) ได้ 95.7% กับ 91.3% และ `3e706a3` (อธิบายเหตุที่ query ถูกปฏิเสธ) ได้ 91.3% กับ 95.7% เคสที่พลาดไม่เกี่ยวกับการค้นชื่อ: `contact-from-evidence` พลาดทุกรอบรวมถึง main, อีกเคสในแต่ละรอบเป็นความผันผวนของ Typhoon (ขอคำชี้แจงหลังถูกแก้ `unsourced_code` หรือเดารหัสวัสดุเป็น `contains "T"` แทนการค้นชื่อ) และไม่ซ้ำเคสเดิมในรอบถัดไป; `chat-redteam-v1` รั่ว 0 ทุกรอบ

### Considered Options

- **จัดอันดับสองรอบ ลำดับปกติกับลำดับกลับด้าน แล้วรวมคะแนนแบบ Borda:** ยังไม่เลือก เพราะต้องเรียก LLM เพิ่มทุกครั้ง และถ้าสองแหล่งมีข้อความเหมือนกัน การสลับลำดับไม่ได้ให้ข้อมูลใหม่
- **ไม่นับคำว่า "รหัส" ตอนคัดแหล่ง:** ไม่เลือก เพราะคำทั่วไปคำอื่นจะทำให้เกิดปัญหาเดิม และวิธีนี้ไม่ได้บอกว่าเต้ารับเป็นวัสดุ
- **ดัชนีค่าข้ามทุกตาราง หรือ BGE-M3:** ทำทีหลัง เพราะต้อง migration หรือต้องมีคีย์ Cloudflare

### Consequences

- ถ้าคำค้นมีคำที่ไม่อยู่ในชื่อจริง เช่น "รหัส เต้ารับคู่มีขั้วสายดิน" ระบบจะค้นไม่เจอ แล้วกลับไปใช้การจัดอันดับอย่างเดียว
- ทะเบียนที่ตั้งชื่อคอลัมน์ต่างจากกติกาจะไม่ถูกค้น เช่น `core.drivers` ใช้ `display_name` ซึ่งตั้งใจไว้ เพราะเป็นชื่อบุคคล

## รวมอันดับด้วย RRF และใช้เป็นความมั่นใจ (เพิ่ม 26 พฤศจิกายน 2569)

ผู้ใช้ส่งเอกสาร "Microsoft AI Engineer: Retrieval Augmented Generation" ซึ่งแนะนำให้ค้นแบบ hybrid (keyword + semantic) แล้วรวมอันดับด้วย Reciprocal Rank Fusion และให้ใช้คะแนน RRF เป็นค่าความมั่นใจ ผู้ใช้ตอบ grill รับทุกข้อ: k = 60, คะแนน RRF แบบ 0–1 แทน `match_score` เดิม, เกณฑ์ pg_trgm ≥ 0.4 และ cosine ≥ 0.5, ใช้กับชื่อวัสดุและคลังเอกสาร, คงโครงสร้าง agent เดิม และแสดงคะแนนเป็นตัวอักษรเล็ก

- เมื่อค้นข้อความแล้วไม่พบแถวที่ตรงตัวในแหล่งข้อมูลที่มี `material_id` แชตทำ embedding ของคำค้น (ปิดข้อมูลแล้ว) ด้วย BGE-M3 บน Cloudflare แล้วถามฐานข้อมูลอีกครั้ง ถ้า embedding หรือการอ่านครั้งที่สองล้มเหลว ใช้ผลค้นข้อความเดิม
- ฐานข้อมูลจัดสองรายการในขอบเขตสิทธิ์และตัวกรองเดิม: ใกล้เคียงทางข้อความ (pg_trgm ≥ 0.4) และใกล้เคียงทางความหมายของชื่อวัสดุ (cosine ≥ 0.5) แล้วรวมด้วย RRF: คะแนน = Σ 1/(60 + อันดับ)
- `match_score` คือคะแนน RRF หารด้วยค่าสูงสุดที่เป็นไปได้ (จำนวนรายการที่ใช้ ÷ 61) อันดับหนึ่งของทั้งสองรายการได้ 1 อันดับหนึ่งของรายการเดียวจากสองรายการได้ 0.5 ถ้าไม่มี embedding จะมีรายการข้อความรายการเดียว และอันดับหนึ่งได้ 1
- คลังเอกสารรวมอันดับแบบเดียวกัน โดยใช้คำถามเป็นรายการข้อความ แต่ `search_knowledge` ยังปิดไว้จนกว่าจะตั้ง `CHAT_DOCUMENTS=on` เพราะตอนนี้ยังไม่มีเอกสาร
- การเขียนคำค้นใหม่ (query rewriting) คือคำค้นที่ LLM เขียนเองใน `query_database` อยู่แล้ว ส่วนการจัดอันดับแถวใช้ RRF ในฐานข้อมูล ไม่เพิ่มการเรียก LLM เพื่อ rerank
- embedding ของชื่อวัสดุเก็บใน `rag.material_name_embeddings` พร้อม md5 ของชื่อ pg_cron เรียกงานรายวันให้ทำ embedding ชื่อที่ยังไม่มีหรือเปลี่ยนชื่อ
- เกณฑ์ 0.4 และ 0.5 เป็นค่าตั้งต้น ต้องปรับจาก eval หลังมีคีย์ Cloudflare
- คะแนน RRF บอกลำดับ ไม่ได้บอกว่าตรงแค่ไหน แถวที่อันดับหนึ่งในรายการเดียวได้ 0.5 แม้ชื่อจะใกล้มาก

## Considered Options

- **PyThaiNLP (ที่ผู้ใช้เรียกว่า ThaiNLP):** ไม่เลือก เพราะใช้ได้กับภาษาไทยอย่างเดียว จับคู่คำไทยกับชื่อพัสดุภาษาอังกฤษไม่ได้ ไม่มีการค้นเชิงความหมายในตัว และต้องตั้ง server Python เพิ่ม
- **ตัวตัดคำไทยของ Node (ICU):** ไม่เลือก เพราะตัดคำเทคนิคผิด เช่น "ล่อฟ้า" ได้เป็น "ล่อ | ฟ้า"
- **BGE-M3 ผ่าน OpenRouter:** ไม่เลือก ผู้ใช้ต้องการแบบฟรี ส่วน OpenRouter ต้องเติมเครดิตขั้นต่ำราว 200 บาท และเครดิตอาจหมดอายุใน 1 ปี
- **Gemini embedding แผนฟรี:** ไม่เลือก เพราะ Google นำข้อความในแผนฟรีไปปรับปรุงบริการได้
- **รันโมเดล embedding เองบน Vercel:** ไม่เลือก เพราะโมเดลและ runtime มีขนาดใหญ่ และ function เปิดเครื่องช้า
- **ตารางคำพ้องที่แอดมินดูแล:** ไม่เลือก เพราะต้องเพิ่มคำเองตลอด
- **ParadeDB pg_search:** ไม่มีให้ใช้บน Supabase
- **embedding ของ Typhoon:** Typhoon ไม่มี API ทำ embedding

## Consequences

- Cloudflare เห็นชื่อพัสดุและคำค้นที่ปิดข้อมูลแล้ว ตามเอกสารของ Cloudflare ระบบไม่เก็บข้อมูลไว้และไม่นำไปเทรนโมเดล
- โควตาฟรีวันละ 10,000 Neurons คิดเป็นราว 9 ล้าน token ถ้าใช้เกินโควตา หรือ Cloudflare ย้าย BGE-M3 ไปแผนเสียเงิน การค้นเชิงความหมายจะใช้ไม่ได้จนกว่าจะแก้ ระหว่างนั้นระบบใช้การค้นแบบใกล้เคียงแทน
- ทุกครั้งที่นำเข้าข้อมูล ต้องทำ embedding ให้ชื่อพัสดุที่เพิ่มหรือเปลี่ยน
